## 1. PLAN.md：新增 "P1 Decisions & Rationale (approved <日期>)"

批准后放在第 3 节 "Agreed decisions" 之后，每条写"决定 + 一句理由 + 对应审计数字"。

- **P1-1 评估协议**
  - 主协议用 A：冻结用户表示，按用户集合评估。B（滚动历史、按事件评估）只作为 S9 的可选补充，不做承诺。
  - 理由：和导出 embedding、`retrieve()`、可评估用户计数、用户级 bootstrap 直接对应。
- **信息边界**
  - 测试的预测时刻是 T_test，历史为 t < T_test，包含 val 期的事件。
  - 所有可学习参数只用 train 拟合，val 只用于早停和调参。
  - ALS：物品因子只用 train 训练，测试用户向量用 train+val 交互 fold-in；另报一行不 fold-in 的结果作参考。
  - Pop：只用 train 计数。
  - 验证集完全对称：冻结在 T_val，历史只用 train。
- **GT 与指标**
  - GT(u) = 测试期内该行为为正的去重物品集合。
  - 依次排除并分别计数：catalog 外物品、`music_id=0`、被已看 mask 的物品、因标签冲突删除的事件。
  - 可评估用户 = 排除后 GT 非空，且至少有 1 条历史。
  - Recall@K = 命中数 / |GT|。
  - NDCG@K 用二值增益，IDCG 按 min(|GT|, K) 个相关物品计算。
  - 所有可评估用户做简单平均。
  - 并列分数按"分数降序、物品下标升序"确定性排序。
  - Bootstrap：用户级重抽样 1000 次，所有模型共用同一组抽样下标，报告均值和模型差值的 CI。
- **冷用户**（T_test 前零历史）
  - 不计入主指标，单独计数，另行报告 Pop 和三塔在冷用户上的结果。
  - 主指标人群正好被 1–5 / 6–20 / >20 三段覆盖。
- **P1-2 历史**
  - 主方案 H1：全部去重事件，加行为编码（long_view、is_like、is_click 等反馈），严格 t < t_pred，取最近 100 条。
  - H2（只用正样本）作为一个受控消融。
  - 相同时间戳的事件一律排除在历史之外；同一时间戳内部按 video_id 确定性排序。
  - 训练、验证、测试和导出共用同一个 `history(u, t_pred)` 函数。
  - 分桶长度 = 实际喂给模型的条数（上限 100），Pop、ALS、三塔用同一种分桶。
  - **History cap 与 mask 分开处理**：
    - 模型输入：取 t < t_pred 的最近 100 条。
    - Seen-item mask（M2）：用 t < t_pred 的**全部**合法交互，不截断。
    - 也就是说，只出现在第 101 条及更早位置的物品不进模型输入，但仍然会被 mask。
    - 两者由两个独立函数产生，不共用截断后的序列。
- **P1-3 切点**
  - 用最近的 CST 午夜：T_val = 2022-04-17 00:00，T_test = 2022-04-26 00:00 CST。
  - 规则：t < T 归前一段，t >= T 归后一段。
- **P1-4 清洗**
  - 完全重复：合并为 1 个事件。
  - 冲突组：按整行选一个代表，取 play_time 最大的行，保证行内标签一致，不逐字段取 max。
  - long_view 或 is_like 不一致的事件：整体删除并计数。
  - tab 5 / 6：去重后保留，tab 不作为特征，报告中单独说明。
  - 不重新推导 long_view 标签，不做 k-core 过滤。
  - `duration_ms=0` 的视频保留，时长按缺失处理。
  - 清洗前后的行数、事件数和各行为正样本数都要报告。
- **P1-5 `music_id=0`**
  - 不作为 music 检索候选，GT 中命中它的计入"sentinel 排除"。
  - 视频任务和训练中完全保留这些交互。
  - 视频塔里用专门的"无音乐"embedding。
- **P1-6 Catalog 与 Masking**
  - 视频 catalog：metadata 全部 7,583 个视频。
  - 音乐 catalog：metadata 中的非零 music ID，共 7,201 个。
  - Mask（M2 主方案）：mask 掉 T_test 前所有交互过的物品；音乐 mask 掉这些视频对应的非零 music ID。
  - mask 只根据预测时刻前的历史计算，不看测试标签；被 mask 的 GT 计数排除。
  - 另外报告 M0（不 mask）作为对照。
- **P1-6b Train-unseen 物品的正确性约束**（新增）
  - **数量**：参考切分下，在 metadata 中但 train 里没有交互的视频约 54 个，非零音乐约 50 个；冷视频实验里还要加上被留出的视频。实际数字以午夜切分为准，由 M2 报告。
  - **总原则**
    - 这些物品始终保留在全量 catalog 和 GT 中，不能因为模型给不出分就把它们剔除。
    - 每个模型只能用它在训练期合法得到的信息打分。打不出分的情况必须有明确规则，**不能让随机初始化、从未训练过的参数影响任何分数**。
    - 对每个模型、每个任务，都报告"GT 落在 train-unseen 物品上的条数"。
  - **Popularity**
    - 分数 = 该行为在 train 中的正样本计数。音乐的计数是该音乐下所有视频的计数之和。
    - unseen 物品的分数为 0。
    - 并列时统一按"分数降序、物品下标升序"排序，所以 unseen 物品排在所有有计数的物品之后。
  - **ALS**
    - unseen 物品没有训练得到的因子。不依赖 `implicit` 内部对空列的初始化结果，**显式把它标为"不可打分"，分数设为 -inf**，排在最后，仍用同样的并列规则。
    - 不能用零向量代替：ALS 的分数可能是负数，零向量物品会排到负分物品前面。
  - **Three-tower**（具体结构留到 D1，以下是 P1 必须满足的约束）
    - 视频、作者、音乐的 ID 词表都只从 train 交互构建。冷视频条件下，被留出的视频不进词表。
    - 不在词表里的 ID 一律映射到共享的 OOV 索引，或者让 ID 分量为零。具体用哪种、OOV 怎么训练（例如 ID dropout），留到 D1。
    - 这类物品的表示只来自内容：视频元数据、音乐塔，以及在词表中的作者 ID。
    - 历史 token 里的物品也遵守同一套映射。
    - 训练、验证、测试和导出共用同一份词表和映射文件，词表在拟合后冻结。
    - 测试要求：断言所有不在 train 词表里的 ID 都映射到 OOV，并且 OOV 之外没有任何"未被梯度更新过"的 ID 行参与打分。
  - **Train-unseen 用户**（同样的约束）
    - 有些用户在 train 中没有交互，但在 val 中有历史，并进入测试主评估。参考切分下约 5% 的测试用户不在 train 中，实际数字由 M2 报告。
    - 三塔：user ID 词表只从 train 构建并冻结；不在词表里的 user ID 映射到 OOV，或让 ID 分量为零，不能用随机初始化、未训练过的 user embedding。这类用户的表示来自历史（以及 U1/U2 中的用户特征）。具体实现留到 D1。
    - ALS：用 train+val 交互做 fold-in，根据已训练的物品因子求解用户向量，不依赖任何未训练过的用户因子。如果一个用户在 T_test 之前没有任何交互，那他就是冷用户，不进入主评估。
    - Pop：与用户无关，不受影响。
    - 报告：主评估中 user ID 为 OOV 的用户数，必要时按"train 中见过 / 没见过"分组报告指标。
    - 测试要求：断言不在 train 中的 user ID 都映射到 OOV，导出时它们的 embedding 也由同一套映射得到。
  - **与 `retrieve()` 一致**
    - 只维护一份 catalog 索引文件（item_id 到行号），评估器、导出和 `retrieve()` 都用它。
    - 导出覆盖全量 catalog 的全部行，包括 OOV 或 unseen 的物品；Pop 和 ALS 一并导出"可打分"的标记。
    - 评估器和 `retrieve()` 调用同一个 top-K 函数，并列规则相同，M2 mask 规则也相同（`retrieve()` 默认开启 mask，可关闭）。
    - 一致性测试覆盖全部 catalog 行，包括 unseen 和 OOV 物品，确认导出分数和直接打分在容差范围内相等。
- **P1-7 重复正样本（评估部分）**
  - 评估用去重二值 GT；music 在 music 粒度去重。
  - 训练时的处理（batch 内重复列 mask、同用户的假负例、共享音乐）留到 D1。
- **P1-8 特征**（已修订：原先的"低风险组"说法收回）
  - 视频 basic 特征可以用，`visible_status` 删除。
  - **证据：用户快照时间无法证明早于预测时刻。**
    - `user_features_pure.csv` 只有一个快照，官方没有写明快照日期。
    - 只读核查结果：
      - 用户 25929 的 `register_days=22`，但从 2022-04-10 起就有日志，所以注册不晚于 04-10，快照不晚于 05-02。这是全体用户中最紧的上界。
      - 另有 12 个用户推出的上界早于 05-08。
      - 数据中没有任何下界。
    - 结论：快照可能落在测试期内（T_test = 04-26 到 05-02 之间），也不能证明早于 T_val。
    - 各字段的风险：
      - `register_days` 和对应的 range 是"到快照日"的天数。只看 range 桶的话，95% 的用户在 366 天以上，对时间不敏感，但桶边界附近的用户会变。
      - `is_video_author`（是否发过视频）和 `is_live_streamer` 都可能在日志窗口内变化。
      - `onehot_feat*` 是加密字段，语义和时间性都无法判断。
      - `user_active_degree` 有 `2_14_day_new` 这类值，和上面用户的 `register_days=22` 对不上，说明各字段可能不是同一时刻计算的。
  - **与作业要求的关系**
    - 作业原文（`docs/assignment.md` 第 24 行）："A user tower using ID, usable metadata, and interaction history."
    - 作业没有定义 "usable"。我们把它解读为"时间上可证明安全"，这是我们自己的解读，不是招聘方的定义。
    - 按这个解读，U0 在字面上缺少用户元数据这一项，存在被认为不满足要求的风险。用户决定接受这一风险，并用"U1 必做"来覆盖要求。
  - **主模型（U0，用户确认）：用户塔不用任何用户快照特征，只用 user ID embedding 加交互历史。**
    - 视频侧的元数据照常使用。
  - **必做实验 U1**：U0 加 `onehot_feat*`（NaN 作为单独类别）、`is_live_streamer`（-124 作为单独类别）、`is_video_author`、`register_days_range`。
    - 这几个字段要么推测是静态的，要么变化慢，但没有证据证明安全。
    - U1 使用和 U0 完全相同的协议，在主评估上报告结果，并做配对 bootstrap，作为对作业 "ID + usable metadata + history" 用户塔的完整实现。
    - 报告中要论证 "usable" 的解读，并说明为什么主结论用 U0。
  - **可选实验 U2**：U1 再加 `user_active_degree` 和 follow / fans / friend 的 range 版本。这组风险更高，只作为探索。
  - **风险说明（写进报告）**：
    - U1、U2 带来的提升既可能是真实信号，也可能来自快照泄漏，离线评估无法区分两者。
    - 所以主表和主要结论只用 U0；U1 是必做的、带风险标注的对照；U2 是可选探索。
  - `is_lowactive_period` 是常量，删除。
- **P1-9 冷视频**
  - 选择：在 train 中见过的视频里，按 train 热度分层随机抽约 10%，固定 seed，完全不看 val / test 标签。
  - 被选中且在测试期有正样本的视频数量作为结果报告，不作为选择条件。
  - 移除：被选视频的所有交互，从训练目标、所有时期的历史（包括测试时 T_test 之前的历史）、batch 负样本、Pop、ALS 和 ID 词表中全部删除。
    - 测试要求：断言冷视频条件下的所有模型输入和拟合数据里都不含被留出集合 H 中的视频。
    - H 中视频的 Music / Author ID 如果在去掉 H 之后的 train 里没出现，按 P1-6b 映射到 OOV。
    - 分组报告：H 中作者在冷 train 中出现过的比例（审计约 23%）、音乐出现过的比例（约 4%）。
  - **公平对照（已修订）**
    - **H 只抽一次**：固定 seed，所有模型、所有条件共用同一个 H。
    - **评估口径一次性固定，与训练条件无关**。用清洗后、未删除 H 的原始日志计算一次，所有模型共用：
      - **GT_H(u)**：测试期内对 H 中视频的正样本，去重，并排除用户在 T_test 前交互过的视频。
      - **M2 mask**：同样用原始日志中 T_test 前的交互计算。它只用于评估，不作为模型输入，也不涉及测试标签，所以不构成泄漏。这样两种条件下的候选集和 GT 完全相同。
      - **评估人群**：GT_H 非空，并且在 T_test 前至少有 1 条不属于 H 的历史事件。这条规则保证用户在冷条件下仍有历史。
    - **两种候选集，所有模型都报告**：
      - (a) 全量 catalog（7,583 个视频，经 M2 mask）：看冷视频能否和热门视频竞争。
      - (b) 只在 H 内排序：看冷视频之间的相对排序。
    - **比较对象分三类，标签不得混用**：
      1. **Cold-video 模型（主角）**：三塔，冷条件训练。
      2. **Cold-condition baselines（同条件对照）**：在同一份去掉 H 的数据上训练的 Pop 和 ALS。按 P1-6b，它们对 H 的分数分别是 0 和 -inf，预期接近 0，用来说明"纯 ID / 协同信号在冷视频上不可用"。另外给出随机排序的解析期望值作为参考线，**按每个用户的实际候选数计算**：
         - 设 C_u 为用户 u 经 M2 mask 后实际可用的候选数：排序 (b) 中是 H 内的候选数，排序 (a) 中是全量 catalog 内的候选数。
         - GT_H(u) 已排除 T_test 前交互过的视频，所以它一定落在候选集内。
         - 每个 GT 物品进入 top-K 的概率是 min(K, C_u)/C_u，所以 E[Recall@K | u] = min(K, C_u)/C_u。
         - E[NDCG@K | u] = (|GT_u|/C_u) · Σ_{r=1..min(K,C_u)} 1/log2(r+1) ÷ IDCG_u。
         - 最后在评估人群上做用户平均，和模型指标的平均方式一致。
      3. **Seen-video Reference**：正常训练（见过 H）的三塔、Pop 和 ALS。**它是参考点，不是严格上界**：冷模型在个别指标上可能超过它，例如 ID embedding 过拟合的时候。它也不是同条件下的冷启动基线，只用来描述"变冷"带来的差距。
    - **主要结论只来自 (1) 对 (2) 的比较**：同一人群、同一 GT、同一候选集、同一训练数据，用配对用户 bootstrap 报告置信区间。(3) 只作为参考线展示。
    - **可选消融**：在冷条件下去掉 music 输入或去掉 author 输入，用同一个 H 和同一评估口径。
    - **范围**：主要指标是 video/long_view 和 video/like。like 在 H 上的正样本可能很少，会报告 GT 条数和用户数，必要时只做描述性展示。
    - **主表隔离**：冷条件模型只用于这个实验；主表仍用正常训练的模型。
